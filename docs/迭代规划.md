# 迭代规划

## 总体节奏

| 阶段 | 周期 | 交付物 | 目标 |
|------|------|--------|------|
| P0 | 2 周 | Agent 核心可用版 | Resume Agent 核心跑通：RuntimeBundle + Agent Loop + 记忆 + Skill，CLI/简单HTML可验证 |
| P1 | 2 周 | Web 服务可用版 | FastAPI + SSE 对话 + 简历下载，单用户完整流程 |
| P2 | 2.5 周 | 多用户版 | 认证 + 多租户隔离 + SQLite 迁移 + 正式 React 前端 |
| P3 | 2 周 | 质量增强版 | PDF 高质量导出 + 领域 Skill 精调 + MCP 工具 + 速率限制 |
| P4 | 持续 | 体验优化版 | 多轮优化 + 简历评分 + 简历对比 + 性能优化 |
| P5 | 2 周 | IM 渠道版 | 飞书/微信接入 + 渠道消息路由 |

> **调整说明**：原 P4（增强版）提前为 P3，原 P5（优化迭代）提前为 P4，原 P3（IM 渠道版）延后为 P5。
> 原因：核心简历生成质量（排版、内容匹配度）是用户最直接的体验问题，优先解决后再扩展渠道。

## P0：Agent 核心可用版 (2 周) ✅ 已完成

**目标**：Resume Agent 核心能力跑通——精简版 RuntimeBundle 构建、Agent Loop、DeepSeek 对接、记忆注入、Skill 加载，通过 CLI 或最简 HTML 页面可验证完整对话流程。

> **设计原则**：P0 聚焦 agent 后端功能，不涉及认证和前端 UI 开发。Web 端仅提供一个极简 HTML 页面用于功能验证。开发模式使用默认 user_id `dev_user`。

### P0-1：项目骨架 + OpenHarness 裁剪 (3 天) ✅ 已完成

| 任务 | 说明 |
|------|------|
| 创建 `resume_agent/` 包结构 | 按架构文档建立目录和模块 |
| 实现 `build_resume_runtime()` | 精简版 RuntimeBundle 构建，跳过本地工具 |
| 接入 DeepSeek API | 配置 OpenAICompatibleClient，支持多 Key 轮询（`api_key_pool.py`） |
| 验证 Agent Loop | 单元测试：提交 prompt → 流式返回 → 工具调用 |

**验收标准**：`resume_agent` 包可 import，`build_resume_runtime()` 可创建能对话的 QueryEngine。

### P0-2：简历领域提示词 + Skill + 记忆 (4 天) ✅ 已完成

| 任务 | 说明 |
|------|------|
| 编写 `resume-skill.md` | 简历优化的领域知识：结构、关键词匹配、STAR 法则等 |
| 系统提示词模板 | 角色定义 + 输出格式约束（Markdown 简历格式） |
| 提示词组装逻辑 | 复用 `prompts/context.py`，注入 resume-skill + 用户记忆 |
| 用户记忆加载 | 按 user_id 加载记忆目录，注入系统提示词 |
| `memory_write` 工具 | LLM 主动调用写入记忆文件（职业偏好、技能标签、优化历史） |
| `skill_loader` 工具 | LLM 主动加载 skill 内容到上下文 |

**验收标准**：对话中要求生成简历，LLM 输出结构化的 Markdown 简历内容；LLM 可通过 `memory_write` 持久化用户偏好并在后续对话中生效。

### P0-3：SSE 对话端点 + 极简验证页面 (3 天) ✅ 已完成

| 任务 | 说明 |
|------|------|
| FastAPI 应用骨架 | 路由注册、中间件、CORS |
| `POST /api/chat` SSE 端点 | SSE 流式对话，StreamEvent → SSE event 推送 |
| `SessionPool` 实现 | 单用户单会话，消息历史内存存储 |

| 极简 HTML 验证页面 | 单文件 HTML + fetch SSE，仅用于功能验证，非正式 UI |

**验收标准**：通过极简 HTML 页面或 curl 发送 prompt，可收到 SSE 流式回复。

## P1：Web 服务可用版 (2 周) ✅ 已完成

**目标**：FastAPI 完整 Web 服务跑通，SSE 流式对话 + 简历渲染下载，单用户完整流程。仍不涉及认证，开发模式下直接使用。

### P1-1：简历渲染与下载 (3 天) ✅ 已完成

| 任务 | 说明 |
|------|------|
| `resume_renderer.py` | Markdown → PDF (fpdf2)，实现渲染队列（同时仅 1 个渲染任务） |
| 简历快照持久化 | LLM 生成简历后自动保存到 `resumes/{resume_id}.md`，与对话会话解耦 |
| `GET /api/resume/{resume_id}/download` | 简历下载端点（使用 resume_id，非 session_id） |
| `GET /api/resume/{resume_id}/preview` | 简历预览端点 |
| `GET /api/resume/templates` | 获取可用简历模板列表 |
| 端到端测试 | 从对话到下载完整流程 |

**验收标准**：对话生成简历 → 调用下载端点 → 获取 PDF 文件；会话淘汰后简历仍可下载。

> **已知问题**：PDF 渲染使用 fpdf2 而非详细设计中规划的 weasyprint（因 weasyprint 需系统级 GTK 依赖），渲染精度较低，将在 P3 阶段解决。

### P1-2：记忆管理 API + 用户配置 + web_fetch (4 天) ✅ 已完成

| 任务 | 说明 |
|------|------|
| 记忆 CRUD API | `GET/PUT/DELETE /api/memory/{doc_name}` |
| 简历上传 | `POST /api/memory/upload`，解析并存为 `简历原文.md` |
| 用户级 Settings | 每用户可覆盖全局配置（简历模板偏好、语言风格等） |
| 记忆注入提示词 | 对话时自动加载用户记忆文件 |
| `web_fetch` 工具 | 抓取 URL 网页内容，用于 JD 链接解析 |

**验收标准**：用户上传简历后，后续对话自动参考原始简历内容；提供 JD 链接后 Agent 自动抓取并分析。

### P1-3：工具与系统 API (3 天) ✅ 已完成

| 任务 | 说明 |
|------|------|
| `GET /api/tools` | 查询可用工具列表 |
| `GET /api/mcp/status` | MCP 服务状态 |

## P2：多用户版 (2.5 周) ✅ 已完成

**目标**：认证体系完整，10 用户并发，每用户独立数据，SQLite 数据存储，正式 React Web 前端上线。

### P2-1：用户认证 + SQLite 迁移 (4 天) ✅ 已完成

| 任务 | 说明 |
|------|------|
| JWT 认证 | 注册/登录/token 刷新 |
| 认证中间件 | SSE 和 REST 都需要鉴权 |
| SQLite 数据库 | 引入 SQLite，认证数据、会话元数据、简历索引迁移 |

| 开发模式默认 user_id 移除 | 切换为正式认证模式 |

**验收标准**：未认证请求被拒绝，JWT 有效期内可正常访问；认证数据存储在 SQLite 中。

### P2-2：多租户隔离 (3 天) ✅ 已完成

| 任务 | 说明 |

| 会话隔离 | 每用户独立会话列表和消息历史 |

## P3：质量增强版 (2 周)

**目标**：解决简历生成的核心体验问题——PDF 高质量排版、领域 Skill 精调提升内容匹配度、MCP 工具扩展能力、速率限制保障稳定性。

> **优先级说明**：核心简历生成质量（排版、内容匹配度）是用户最直接的体验瓶颈，优先于渠道扩展。

### P3-1：简历结构化渲染引擎 (5 天) ✅ 已完成

| 任务 | 说明 | 状态 |
|------|------|------|
| ResumeData 数据模型 | Pydantic 结构化简历数据模型（姓名/联系方式/工作经历/教育/技能/项目） | ✅ 已完成 |
| Markdown → ResumeData 解析器 | 将 LLM 输出的 Markdown 解析为 ResumeData，容错处理格式不一致 | ✅ 已完成 |
| Jinja2 HTML 模板引擎 | 替代 python-markdown + CSS overlay，每套模板为完整 HTML+CSS 文件 | ✅ 已完成 |
| professional 模板 | 双栏侧边栏布局（左：技能+联系方式，右：经历+教育） | ✅ 已完成 |
| academic 模板 | 传统单栏居中布局，标题装饰线 | ✅ 已完成 |
| creative 模板 | 卡片式布局，圆角阴影，渐变色块 | ✅ 已完成 |
| SSE resume_data 事件 | LLM 输出完毕后推送结构化 ResumeData JSON | ✅ 已完成 |
| 前端 ResumePreview 组件 | 接收 ResumeData 渲染所见即所得简历预览 | ✅ 已完成 |
| 前端 SSE 事件处理 | 流式 Markdown → 收到 resume_data → 自动升级为组件渲染 | ✅ 已完成 |
| 双格式快照持久化 | 同时保存 ResumeData JSON + Markdown 原文 | ✅ 已完成 |
| 渲染引擎集成 | ResumeData + Jinja2 模板 → weasyprint/xhtml2pdf → PDF | ✅ 已完成 |
| 降级兼容 | 旧快照（仅有 .md）自动解析为 ResumeData 渲染 | ✅ 已完成 |

**验收标准**：
1. 用户生成简历后，前端自动从 Markdown 显示升级为精美的结构化简历预览
2. 三套模板视觉差异明显（不同布局，不仅是配色）
3. PDF 下载效果与前端预览一致
4. 即使 LLM 输出格式有偏差，仍能正确解析和渲染

### P3-2：领域 Skill 精调 + 智能模板匹配 + 输出标记分隔 (3 天)

| 任务 | 说明 | 状态 |
|------|------|------|
| 简历输出标记分隔 | 系统提示词要求 LLM 用 `<!--RESUME-->` / `<!--/RESUME-->` 包裹简历正文，建议内容放在标记外；截取逻辑从黑名单改为标记提取（主路径）+ 白名单过滤（降级路径）；流式推送时自动过滤标记标签 | ✅ 已完成 |
| `resume-skill.md` 迭代 | 根据实际使用反馈优化提示词，增加具体的输出格式约束和示例 | |
| 行业细分 Skill | `resume-tech.md`、`resume-finance.md` 等行业专项技能文件 | |
| JD 解析 Skill | 招聘需求结构化提取（硬技能/软技能/行业术语分类提取） | |
| 系统提示词优化 | 增强输出格式约束，减少 LLM 输出结构不一致的问题 | |
| 行业→模板映射 | 根据解析出的行业/岗位类型自动推荐最佳模板（`template_hint`） | |
| 智能模板推荐 API | `GET /api/resume/template-hint?jd=...` 根据岗位描述推荐模板 | |

**验收标准**：不同行业 JD 的简历匹配度明显提升，LLM 输出的简历格式统一规范，系统能根据岗位自动推荐合适的简历模板；简历渲染不再包含"优化要点"等非简历内容。

### P3-4：速率限制 + 监控 (2 天)

| 任务 | 说明 |
|------|------|

## P5：IM 渠道版 (2 周)

**目标**：飞书/微信可收发消息，对话生成简历。

> **前置条件**：P3（质量增强版）完成，核心简历体验达标后再扩展渠道。

### P5-1：消息网关基础设施 (3 天)

| 任务 | 说明 |
|------|------|
| `channels/` 模块搭建 | ChannelAdapter 基类 + InboundMessage/OutboundMessage 消息模型 |
| MessageBus 实现 | inbound/outbound 消息总线分发 |
| GatewayBridge 集成 | 渠道消息到 SessionPool 的桥接 |
| 渠道消息统一分发 | Web / 飞书 / 微信消息统一进入 SessionPool |

**验收标准**：MessageBus 可分发消息，GatewayBridge 可将渠道消息桥接到 SessionPool。

### P5-2：飞书渠道接入 (3 天)

| 任务 | 说明 |
|------|------|
| 复用 `FeishuAdapter` | 从 OpenHarness `channels/impl/feishu.py` 移植 |
| 飞书事件订阅 | 配置 Webhook URL + 验证 token |
| sender_id → user_id 映射 | 首次消息自动创建用户 |
| 消息长度处理 | 超长回复分段发送 |

**验收标准**：飞书发消息 → Agent 回复 → 简历内容以消息形式返回。

### P5-3：微信/企微渠道 (3 天)

| 任务 | 说明 |
|------|------|
| `WeChatAdapter` 实现 | 实现 `ChannelAdapter` 接口 |
| 企业微信 Webhook | 接收消息 + 发送回复 |
| 消息格式适配 | 微信消息格式（文本/Markdown 卡片） |
| 渠道特定处理 | 各渠道的消息格式差异处理 |

**验收标准**：企业微信发消息 → Agent 回复；同一用户在飞书和 Web 端的会话数据共享。
