# 项目架构

## 1. 产品定位

Resume Agent 是一个基于 OpenHarness 重构的简历智能体，核心能力是结合用户简历与招聘岗位 JD，智能生成匹配岗位的优化简历，支持 Web 下载和飞书/微信等第三方渠道交互。

| 属性 | 值 |
|------|-----|
| 产品形态 | 云端 Web 服务 + IM 渠道接入 |
| 目标并发 | 10 用户同时在线 |
| LLM 后端 | DeepSeek API（OpenAI 兼容协议，多 Key 轮询） |
| 部署环境 | 轻量级云服务器（单机） |
| 底层框架 | OpenHarness v0.1.6（裁剪复用） |

## 5. 核心数据流

### 5.1 Web 端对话流

```
用户输入 (Web UI)
  ↓ POST /api/chat {prompt, session_id}
  ↓ [认证中间件] JWT → user_id（P0/P1 开发模式下跳过，使用默认 dev_user）
FastAPI POST /api/chat (SSE)
  ↓
SessionPool.get_or_create(user_id, session_id)
  ↓ 返回该用户的 QueryEngine + Messages
QueryEngine.submit_message(prompt)
  ↓
run_query() — Agent Loop
  ├── auto_compact_if_needed()
  ├── OpenAICompatibleClient.stream_message() → DeepSeek API (多 Key 轮询)
  ├── tool_use? → execute_tool()
  │   ├── memory_write (记忆写入)
  │   ├── web_fetch (网页抓取)
  │   ├── mcp__email__send (HTTP MCP, 用户级认证注入)
  │   ├── mcp__pdf__convert (HTTP MCP)
  │   └── skill_loader (skill 加载)
  └── StreamEvent 流
  ↓
StreamEvent 序列化为 SSE event → 流式推送
  ↓
Web UI 渲染 (流式 Markdown + 工具调用展示)
```

### 5.2 飞书/微信渠道流

```
用户在飞书/微信发消息
  ↓ HTTP Webhook
ChannelAdapter (FeishuAdapter / WeChatAdapter)
  ↓ InboundMessage
MessageBus.consume_inbound()
  ↓
GatewayBridge.process_message()
  ↓
SessionPool.stream_message()
  ↓
QueryEngine → DeepSeek API → 流式回复
  ↓
GatewayStreamUpdate → OutboundMessage
  ↓
ChannelAdapter → 飞书/微信 API 回复
```

### 5.3 简历生成与下载流

```
用户对话中明确要求生成简历
  ↓
LLM 调用 skill 工具加载 resume-skill.md
  ↓
LLM 生成 Markdown 格式简历 (流式输出到前端)
  ↓
Agent 检测到简历输出 → 自动保存简历快照
  → 存储到 ~/.resume_agent/users/{user_id}/resumes/{resume_id}.md
  → 通过 SSE 推送 resume_id: {"type": "resume_generated", "resume_id": "..."}
  ↓
前端展示 + 提供"下载 PDF"按钮
  ↓
GET /api/resume/{resume_id}/download?format=pdf
  ↓
resume_renderer.py: Markdown → PDF (weasyprint, 渲染队列)
  ↓
返回 PDF 文件流
```

> **注意**：下载端点使用 `resume_id`（而非 `session_id`），确保会话被 LRU 淘汰后简历仍可下载。

### 6.2 运行时隔离

| 资源 | 隔离级别 | 说明 |
|------|----------|------|
| QueryEngine | 每会话 | 每用户每会话独立的对话历史和引擎 |
| Messages | 每会话 | 对话消息隔离 |
| Memory | 每用户 | 专属记忆文档，注入提示词时按 user_id 加载 |

| Session Pool | 进程级共享 | 管理所有活跃会话，LRU 淘汰空闲会话 |

## 7. MCP 集成策略

### 7.1 仅使用 HTTP Transport

云服务器无法启动本地子进程，只配置 HTTP 类型的 MCP Server：

```json
{
  "mcp_servers": {
    "pdf-converter": {
      "type": "http",
      "url": "http://localhost:9100/mcp",
      "headers": {}
    },
    "email-sender": {
      "type": "http",
      "url": "https://mcp-email-service.example.com/mcp",
      "headers": {"Authorization": "Bearer xxx"}
    }
  }
}
```

### 7.2 stdio MCP 的云端适配

对必须使用的 stdio MCP 工具，在云服务器内部署代理：

```
云服务器内部:
  stdio MCP server (子进程) ←→ stdio-to-http proxy ←→ Resume Agent
```

### 7.3 多用户 MCP 认证动态注入

ToolRegistry 为进程级单例，工具定义全局共享。但部分 MCP 工具（如邮件发送）需要按用户传入不同的认证信息。

解决方案：工具定义在 Registry 中全局共享，执行时从用户上下文动态获取认证信息：

```
全局: weather MCP (无需认证，所有用户共享)
用户级: email MCP (每用户独立 auth token，执行时动态注入)
```

`mcp_auth.py` 在执行 MCP 调用前，合并全局配置 + 用户级认证信息（详见详细设计 7.3 节）。

## 8. 认证体系

> **注意**：认证功能在 P2 阶段实现。P0/P1 为开发模式，不要求认证，使用默认 user_id `dev_user` 直接访问。

### 8.1 用户认证

| 认证对象 | 方式 | 管理模块 |
|----------|------|----------|
| Web 用户 | 账号密码注册/登录 + JWT Token | `backend/routes/auth.py` |
| 飞书用户 | 飞书开放平台事件订阅 + 验证 token | `backend/routes/auth.py` |
| 微信/企微用户 | Webhook token + 消息签名验证 | `backend/routes/auth.py` |

用户通过账号密码登录后即可使用完整服务，无需额外配置。DeepSeek API Key 等 Provider 凭证由服务端内置管理，对用户完全透明，无需用户感知或配置。

### 8.2 IM 渠道认证

- **飞书**：通过飞书开放平台的事件订阅 + 验证 token
- **微信/企微**：通过 webhook token + 消息签名验证
- 渠道用户通过 `sender_id` 映射到系统内 `user_id`，首次消息自动创建用户

| 数据存储 | 文件存储(P0/P1) → SQLite(P2) | P2 迁移到 SQLite 提升并发安全 |
| 部署 | systemd / Docker | 单机部署 |
| 数据验证 | Pydantic v2 | 复用 OpenHarness 的模型体系 |
